# REVIEW.md

Review of the starter `app/main.py` (commit "Starter code from candidate kit"). Line numbers refer to the starter.
"Reproduced" means I ran the starter code with that input and saw the wrong result.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | module, `MongoClient(...)` l.22 | Client is not `tz_aware`, so PyMongo returns **naive** datetimes. Mixing them with aware values raises `TypeError`; treating them as local time shifts them by the server's offset. | Reproduced: `compute_overtime` with a naive punch-out read from Mongo raises `TypeError: can't subtract offset-naive and offset-aware datetimes` -> 500. | `MongoClient(..., tz_aware=True, tzinfo=UTC)`; every instant is aware UTC, converted to epoch ms only at the API boundary (`ms_to_dt` / `dt_to_ms`). |
| 2 | `compute_late_minutes` l.33-37 | (a) Grace test `minutes > 10` runs on *floored* minutes, so anything up to 09:40:59 counts as on time. (b) `punch_in.replace(hour, minute)` builds the shift start in whatever zone the punch is in (UTC/naive), not IST. (c) Overnight shifts use the wrong day. | Reproduced: 09:40:01 -> 0 (want 10); 09:40:59 -> 0 (want 10); 10:05 IST given as UTC -> 0 (want 35); 00:30 punch on a 22:00 shift -> 0 (want 150). | Compare whole **seconds** `> 600`, then `floor(seconds / 60)`; shift start is built as an IST instant on the record's attendance date (R1, R2). |
| 3 | `compute_work_hours` l.40-41 | Uses float `round()`: half-to-even and binary error, not half-up. No truncation to seconds. | Reproduced: 450 s -> 0.12 (want 0.13); 1026 s -> 0.28 (want 0.29). | Whole seconds as `Decimal / 3600`, `quantize(..., ROUND_HALF_UP)` (R4). |
| 4 | `compute_overtime` l.44-47 | (a) No 30-minute minimum. (b) Overnight shift end is put on the record's date instead of the next day. | Reproduced: out 18:35 -> 5 (want 0); overnight out 06:40 next day -> 1480 (want 40). | `minutes >= 30 else 0`; shift end + 1 day when `shift_end <= shift_start` (R1, R3). |
| 5 | `health` l.72-74 | Always returns 200; never checks MongoDB, so the readiness probe lies. | Stop MongoDB: `/health` still says ok. | `ping` with a 5 s server-selection timeout; 503 on failure. |
| 6 | `create_employee` l.79-83 | Check-then-insert with no unique index: two concurrent creates both pass `find_one` and both insert. | 8 parallel POSTs with the same `emp_code` -> several 201s and duplicate documents. | Unique index on `emp_code`, created at start-up; insert and map `DuplicateKeyError` to 409. |
| 7 | `EmployeeIn` l.53-60 | No validation: any `emp_code`, email, `HH:MM` or date is accepted; `shift_start == shift_end` accepted. Bad shift strings crash later endpoints (500). | POST `shift_start: "9:30"` -> 201, then punch-in -> 500. | Field patterns/lengths from the contract (ASCII `[0-9]` so Unicode digits are rejected), real-date check for `joined_on`, model validator for equal shifts -> 422. |

| 9 | `list_employees` l.93 | `skip = page * page_size` skips a whole page: page 1 shows records 21-40. | Create 3 employees, GET `?page=1` -> empty list. | `skip = (page - 1) * page_size` (R10). |

| 11 | `punch_in` l.101, 113 | Unknown employee is not handled: `emp` is `None`, `emp["shift_start"]` raises `TypeError`. | POST punch-in for `EMP9999` -> 500 (want 404). | `get_employee_or_404`. |
| 12 | `punch_in` l.102-103 | `datetime.fromtimestamp(ms/1000)` uses the **server's** local zone and keeps milliseconds; the date is that local date, not the IST date, and overnight shifts are ignored (R1). | Reproduced on a UTC server: a 00:30 IST punch-in gets date `2026-07-06` instead of `2026-07-07`; a 05:30 punch on a 22:00-06:00 shift gets the wrong day. | `ms_to_dt` (aware UTC, truncated to seconds) + `attendance_date()` implementing R1 in IST. |
| 13 | `punch_in` l.104-118 | Check-then-insert race and no unique index: two simultaneous punch-ins both get 201 and create two records for one day. | 10 parallel identical punch-ins -> more than one 201. | Unique index on `(emp_code, date)`; insert and map `DuplicateKeyError` -> 409. |

| 16 | `list_attendance` l.144-147 | Loads **every** matching document into Python, then sorts and slices in memory. | 17 | `list_attendance` l.124-143 | No validation: `date_from > date_to`, malformed dates, unknown `status`, `page=0` all accepted. | `?date_from=2026-07-10&date_to=2026-07-01` -> 200 empty (want 422). | `parse_date`, range check, `Literal` status, bounded paging -> 422. |
| 18 | module | No indexes are created, so every query is a collection scan and the uniqueness guarantees above do not exist. | `/admin/explain` shows `COLLSCAN`. | `ensure_indexes()` at start-up (idempotent), retried from `/health` if MongoDB was not up yet. |
| 19 | module | A database error becomes a 500. | Stop MongoDB, call any endpoint -> 500. | Exception handler maps `PyMongoError` to 503. |

## Examined and judged not to be defects

* `load_dotenv()` (l.20): its default is `override=False`, so real environment variables already win over `.env`. Kept (made explicit).
* The `mongodb://localhost:27017` / `attendance_db` fallbacks: local-development defaults with no credentials, the same ones the kit's `sample_seed.py` uses. The grader's `MONGO_URI` / `MONGO_DB` always take priority.
* Module-level `MongoClient`: PyMongo connects lazily and the client is thread-safe, so one shared client is correct for FastAPI's thread pool.
* Default `shift_start` / `shift_end` of 09:30 / 18:30 in `EmployeeIn`: matches the contract defaults.
* Comparing `date` strings with `$gte` / `$lte`: correct, because `YYYY-MM-DD` sorts lexicographically in date order.
